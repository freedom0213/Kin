# Kin 补充体验设计决策

> 文档状态：持续补充中，包含已确认方向、真机缺陷和待专项验证事项
> 创建日期：2026-07-30
> 最近更新：2026-07-31
> 适用范围：移动端聊天、碰一碰配对、好友上线、登录注册、个人主页、本地数据与测试账号
> 说明：本文记录已经讨论并确认的产品方向，方便后续继续补充细节。它不是当前功能已经完成的声明。

## 一、总体目标

Kin 的差异化不应依赖大量装饰特效，而应让几个关键时刻具有清晰、克制且有生命感的反馈：

- 发出消息时，用户能感受到消息从输入区域进入对话。
- 两名用户主动开启碰一碰后，系统明确展示寻找、发现、确认和成功状态。
- 碰一碰确认窗口能够体现对方的个人名片，同时优先保证身份核验。
- 好友上线时，状态变化具有连贯的前后节奏。
- 登录与注册页面延续 Kin 的“靠近、相遇、连接”视觉语言。
- 测试阶段优先保证核心流程验证，暂不实现正式账号找回体系。

所有持续动效和关键过渡都需要支持系统“减少动态效果”。动效不能阻塞操作，也不能让低端设备明显掉帧。

## 三、消息气泡发送动画

### 3.1 目标

点击发送后，用户应感受到新消息从输入栏进入会话，而不是毫无过渡地出现在消息列表中。

### 3.2 推荐表现

发送自己的文字消息时：

1. 发送按钮轻微收缩后恢复，可配合一次轻触觉反馈。
2. 新气泡在右侧出现，从下方向上移动约 6～10 像素。
3. 气泡同时从约 `0.96` 缩放至正常大小，并由透明过渡为完全显示。
4. 动画总时长建议为 180～240 毫秒。
5. 保留当前聊天背景的消息涟漪，但涟漪不能抢过气泡本身。

收到对方消息时使用相同语言，但从左侧轻微进入，以表达消息来源。

### 3.3 约束

- 只有新到达或刚发送的消息播放进入动画。
- 加载历史记录、重新进入会话和列表重新渲染时不得批量播放。
- 连续快速发送时缩短或合并背景涟漪，避免界面反复闪动。
- 开启“减少动态效果”时直接显示气泡，只保留必要的状态反馈。
- 不使用夸张弹跳、旋转或长时间晃动。

## 四、单一“开启碰一碰”入口

### 4.1 核心规则

- 添加好友页面只向用户展示一个主要按钮：`开启碰一碰`。
- 两名用户都必须主动按下“开启碰一碰”，才能进入可配对状态。
- 未主动开启时，Kin 不在后台持续寻找其他用户。
- 用户界面不展示“发起方”“接收方”等底层技术角色。
- 底层仍可根据 NFC 和平台能力分配技术角色，但这个过程对用户隐藏。
- 双方发现彼此后，仍然必须分别确认，不能因为手机靠近就自动成为好友。

### 4.2 添加好友页面说明文案

首版推荐文案：

> 你和对方都开启碰一碰后，将两台手机背面靠近。
> 发现对方后，只有双方确认，才会成为好友。

主按钮：

```text
开启碰一碰
```

可以在按钮下方使用低视觉权重的补充说明：

```text
碰一碰只会在你主动开启时工作
```

### 4.3 状态流程

```text
未开启
  ↓ 用户点击“开启碰一碰”
正在开启
  ↓ NFC 与配对会话准备完成
已开启，等待碰一碰
  ↓ 发现另一台同样已开启的设备
发现对方
  ↓ 展示名片并分别确认
等待对方确认
  ↓ 双方均确认
已经成为好友
```

失败或中断时允许进入：

- NFC 不可用
- 权限或系统能力不足
- 没有发现对方
- 配对等待超时
- 对方取消
- 当前用户主动关闭碰一碰

### 4.4 等待状态建议

点击按钮并成功开启后，出现碰一碰等待半弹窗：

- 标题：`碰一碰已开启`
- 说明：`请让对方也开启碰一碰，然后将两台手机背面靠近`
- 中间显示两台手机缓慢靠近的图形。
- 提供明确的 `停止碰一碰` 或 `取消` 操作。
- 沿用当前配对会话的有效期；具体等待时长以现有配置和两台真机验证结果为准。

### 4.5 技术边界

当前 NFC 实现仍需要两台真实设备验证。特别需要确认：

- 当前 Expo 开发版 APK 是否能完成手机对手机的数据交换。
- Android 不同品牌和系统版本的 NFC 行为是否一致。
- iOS 是否必须显示系统 NFC 扫描界面。
- 两台设备都点击同一个按钮后，底层如何稳定确定读取方和提供数据的一方。

在上述能力验证完成前，不能在产品文案中承诺“任何时候直接碰一下即可”。当前承诺应限定为：

> 双方打开 Kin 并开启碰一碰后，即可将手机靠近。

在 NFC 能力尚未完成双机验证期间，配对码作为正式备用方案保留：

- 配对码必须可以独立完成发现对方、展示名片、双方确认和添加好友的完整流程。
- NFC 和配对码只负责“如何发现对方”，发现后的名片确认、等待对方确认和成功状态必须共用同一套业务逻辑。
- 不得为了实现 NFC 复制另一套好友关系或确认流程。
- NFC 不可用、权限不足或设备不兼容时，页面明确提供“使用配对码”入口。
- 当前阶段可以先完成统一页面、状态机和配对码流程；真实 NFC 传输根据两台真机验证结果继续接入。

## 五、碰一碰名片弹窗

### 5.1 核心视觉要求

名片背景图不作为整个弹窗的填充背景，而是作为头像附近的一块独立图片区显示。

背景图显示规则：

- 保持资料页中使用的原始宽高比例。
- 不裁剪图片内容。
- 不拉伸或压缩变形。
- 不使用 `cover` 方式强行填满正方形弹窗。
- 不把图片放大到超出其名片区域。
- 不在整张图片上覆盖深色或彩色遮罩。
- 图片区域不足以填满弹窗时，剩余空间使用 Kin 的稳定浅色表面，不模糊放大图片补齐。

现有背景名片采用横向比例时，弹窗中也保持相同的横向比例。实现概念接近 `contain`，而不是 `cover`。

### 5.2 推荐布局

```text
┌────────────────────────┐
│    对方名片背景原比例图   │
│                        │
│          [头像]         │  ← 头像贴近或轻微压在图片区下缘
├────────────────────────┤
│          对方昵称        │
│         @username       │
│                        │
│  请确认这是你正在见的人   │
│  只有双方确认后才会成为好友│
│                        │
│   [取消]       [确认]    │
└────────────────────────┘
```

头像与背景图的分离优先使用：

- 头像外圈边框；
- 轻微阴影；
- 图片区域与信息区域的自然边界。

不通过给整张名片背景加暗色遮罩解决头像可见性。

### 5.3 内容优先级

弹窗依次展示：

1. 名片背景和头像，用于快速识别人。
2. 昵称。
3. 用户名，用于防止重名误认。
4. 双方确认说明。
5. 取消和确认按钮。

名片背景负责个性表达，但不能弱化用户名和双方确认规则。

### 5.4 数据与隐私影响

当前个人资料和好友列表已经支持背景名片，但配对对象数据尚未包含背景名片字段。实现时需要调整：

- 后端配对对象摘要；
- 移动端 `PairingPeer` 类型；
- 配对更新 WebSocket 数据；
- 图片地址解析、缓存和加载失败降级；
- 资料页中关于“谁能看到背景名片”的说明。

因为配对窗口发生在成为好友之前，现有“背景名片只展示给好友”的表述需要在实现时重新统一。

已确认采用以下隐私边界：

- 双方都主动开启碰一碰或主动进入配对码流程后，系统才允许交换配对名片数据。
- 成功发现对方后，可以在成为好友之前临时显示背景名片，用于确认眼前的人。
- 未进入有效配对会话的陌生用户不能查询背景名片。
- 用户取消、对方取消或配对超时后，不把对方名片保存为联系人资料。
- 只有双方分别确认后，才建立正式好友关系并进入正常好友资料权限范围。

## 六、好友上线动画

### 6.1 选定方向

采用三阶段“苏醒”编排，让用户看见好友从离线状态进入在线状态的完整过程。

### 6.2 动画节奏

第一阶段：状态点亮

- 原位置的状态点由离线色平滑过渡为 Kin 绿。
- 会话行背景出现非常轻的颜色响应。

第二阶段：会话项迁移

- 会话项从 Offline 分组移动到 Online 分组。
- 移动路径保持连续，避免先消失再突然出现在另一处。
- 列表中的其他会话项平滑让位。

第三阶段：落位反馈

- 好友到达 Online 分组后，头像产生一次短促扩散。
- 会话行出现一次从左向右或由头像向外扩散的浅绿色提亮。
- 随后进入现有的低强度头像呼吸状态。
- 可配合一次可关闭的上线提示音或轻触觉反馈。

整体动画建议控制在约 700～900 毫秒内。各阶段需要有先后关系，不能全部同时播放。

### 6.3 约束

- 不增加大量粒子、闪光或持续高速动画。
- 多名好友同时上线时应错开或合并反馈，不能阻塞列表操作。
- 首次加载好友列表时不播放“上线”动画，只在真实离线到在线事件发生时播放。
- 开启“减少动态效果”时只更新分组和状态文本，不播放迁移与扩散动画。

## 七、登录和注册页面

### 7.1 选定方向

采用“靠近场”抽象背景，延续 Kin 的物理靠近和在线呼吸语言。

### 7.2 视觉构成

- 页面纳入全局方案 A「Graphite Flow」，使用接近黑色的哑光石墨背景，不再使用雾灰、浅冷灰或纯白作为页面主体。
- 背景包含两个低透明度、边缘柔和的抽象色域。
- 两个色域以非常缓慢的速度靠近和分离，表达人与人之间的距离。
- 抽象色域必须压低亮度和饱和度，不能破坏高级黑基底。
- 使用低饱和 Kin 绿作为唯一主要强调色。
- 输入框、按钮、规则提示和错误信息使用 Graphite Flow 的统一深色表面层级，确保在登录前后仍属于同一套产品视觉。
- 避免通用彩色渐变、摄影大图、霓虹和高密度粒子。
- 登录与注册共用同一视觉世界，不能像两套页面。

### 7.3 登录页

建议结构：

1. Kin 品牌名称。
2. `只和见过的人聊天`。
3. 用户名和密码字段。
4. 密码显隐按钮。
5. 登录按钮。
6. 前往注册的次要入口。

登录成功时，两个背景色域可以短暂靠近并稳定下来，然后进入会话列表。过渡不能延迟正常登录。

### 7.4 注册页

注册页与登录页保持相同背景和排版语言，并补充：

- 持久可见的字段标签，不能只依赖占位文字。
- 用户输入文字必须显式指定深色，不依赖系统主题的默认文字颜色。
- 占位文字、光标和选中文字颜色也需要明确指定。
- 用户名规则的行内提示和验证。
- 密码显隐。
- 密码规则的实时完成状态。
- 确认密码字段。
- 注册失败时在对应字段附近提供明确恢复方式。

测试阶段暂不在注册页承诺密码找回能力。

## 八、测试阶段账号与密码策略

### 8.1 当前决定

测试阶段暂不开发“忘记密码”和账号找回功能，先使用预先准备的测试账号和密码验证核心流程。

### 8.2 测试账号约束

- 测试账号只能用于开发版和内部测试环境。
- 使用无真实隐私数据、可随时删除的账号。
- 测试密码不得复用开发者或测试人员的真实密码。
- 不应把具有实际权限或长期价值的秘密硬编码进移动端。
- 如果需要在测试页面显示账号，应明确标记为“测试账号”。
- 正式发布前必须移除测试入口、测试凭据和自动填充逻辑。

### 8.3 预留测试账号

后续在开发/测试环境预先创建以下三个专用账号，减少每次安装 Expo 开发版 APK 后重复注册的成本：

| 用途 | 用户名 | 密码 | 状态 |
|---|---|---|---|
| 测试账号 A | `kin_test_01` | `KinTest01!` | 已预置，与 B 为好友 |
| 测试账号 B | `kin_test_02` | `KinTest02!` | 已预置，与 A 为好友 |
| 测试账号 C | `kin_test_03` | `KinTest03!` | 已预置，初始无好友 |

实现要求：

- 三个账号仅存在于开发或内部测试环境，不授予管理权限。
- 账号中不得存放真实个人信息、隐私图片或具有长期价值的数据。
- 登录页可以在开发构建中提供测试账号提示或快速填入入口；生产构建必须移除。
- 是否通过后端初始化脚本、测试环境启动脚本或管理员命令创建，由检查现有后端账号架构后决定。
- 如果现有用户名或密码规则不接受上述格式，需要保持编号语义并在本章同步更新最终凭据，不能静默改变。

当前实现：

- 可以在后端目录运行 `python scripts/seed_test_accounts.py` 幂等创建或刷新测试账号。
- 测试部署也可以显式设置 `KIN_SEED_TEST_ACCOUNTS=1`，在后端启动时初始化。
- 默认不开启自动预置，避免生产环境意外出现公开测试账号。
- 重复执行初始化不会覆盖账号已经激活的 E2E 公钥。
- 重复执行不会删除测试账号 C 后续通过配对流程建立的好友关系。

### 8.4 测试账号的设备密钥

预置账号没有注册页面生成密钥的过程，因此采用“首次登录激活”策略：

- 每个账号在当前设备使用独立的 SecureStore 密钥名称，不再共用全局 `kin_secret_key`。
- 测试账号首次登录某台设备时生成该账号的 Curve25519 密钥对。
- 私钥只保存在当前设备；公钥通过认证接口上传后提供给好友进行端到端加密。
- 后续在同一设备登录同一账号时复用该账号自己的密钥。
- 账号之间切换不会覆盖其他账号的私钥。
- 当前阶段不支持完整多设备密钥恢复；同一账号在新设备首次登录会轮换公钥，旧设备可能无法继续使用该账号的加密身份。
- 好友在线时会收到公钥变更事件；离线好友下次刷新好友列表时取得最新公钥。

正式多设备支持仍需要恢复包、设备管理和密钥轮换确认，不包含在本次测试账号功能内。

### 8.3 暂缓但需要保留的后续议题

正式账号体系实施前，需要重新讨论：

- 是否允许绑定邮箱；
- 是否采用恢复短语或恢复包；
- 用户换机时如何恢复端到端加密私钥；
- 旧设备丢失时是否允许轮换密钥；
- 密钥轮换后好友是否需要重新确认身份；
- 旧聊天记录是否可以恢复。

## 九、注册页密码输入可见性

### 9.1 真机现象

用户名输入为深色文字，但密码输入显示为白色；输入框背景同样接近白色，用户无法判断已经输入了多少位密码。页面也没有密码显隐按钮。

### 9.2 当前代码结论

登录和注册页的 `TextInput` 样式只指定了浅色背景，没有显式指定输入文字颜色。部分设备或系统主题可能把密码输入文字应用为浅色默认值，因此出现白字白底。

这是代码层面可以确认的问题，不应仅依赖更换页面背景解决。

### 9.3 修复要求

- 用户名、密码和确认密码输入框显式使用统一的深色文字。
- 显式设置占位文字颜色、光标颜色和选中颜色。
- 密码输入框右侧增加小眼睛按钮。
- 默认隐藏密码；点击后显示明文，再次点击恢复隐藏。
- 小眼睛按钮点击区域不小于 44×44，并提供无障碍名称。
- 明文和隐藏状态切换时不能清空密码、改变光标位置或让输入框失焦。
- 密码下方可展示已输入位数或规则完成状态，但不得显示实际密码内容。

### 9.4 验收标准

- 浅色和深色系统主题下密码都清晰可见。
- 至少在两台当前测试手机上验证。
- 密码隐藏时能辨认已输入字符数量。
- 显隐切换不会导致键盘关闭或输入内容丢失。

### 9.5 实施结果（2026-07-31）

- 登录页和注册页已共用统一的密码输入组件，避免两套显隐逻辑产生差异。
- 用户名和密码输入均显式指定文字、占位、光标和选中颜色，不再依赖系统主题默认值。
- 密码默认隐藏，右侧眼睛按钮可切换显示与隐藏，点击区域不小于 44×44。
- 显隐切换保留受控密码值、输入焦点和光标选择位置，并提供“显示密码 / 隐藏密码”无障碍名称。
- 登录密码使用当前密码自动填充语义，注册密码使用新密码自动填充语义。
- 本阶段没有新增确认密码字段和实时规则状态；这些仍属于第 7.4 节后续注册流程完善范围。
- 已增加自动化回归检查，最终仍需在浅色/深色系统主题和两台测试手机上验收。

## 十、聊天消息提示音

### 10.1 当前问题

接收消息时已有应用内提示音，但真机测试中音量偏小，音色也缺乏 Kin 的辨识度。

当前实现使用代码内嵌的短 WAV 音频，并以约 `0.18` 的播放器音量播放；Android 后台系统通知则仍使用系统默认声音。应用内声音与后台通知声音目前不是同一套听觉语言。

### 10.2 可选方案

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|---|
| 调整现有内嵌音频 | 提高播放音量并修改现有波形 | 改动最小 | 现有音色基础较弱，仍可能不好听 | 临时测试 |
| 使用系统默认提示音 | 交给 Android/iOS 播放系统声音 | 稳定、用户熟悉 | 缺少 Kin 辨识度，不同手机差异明显 | 可靠性优先的早期版本 |
| 使用独立 Kin 声音资源 | 将设计好的 WAV/M4A 作为正式资源打包 | 音色、响度和品牌一致性最好 | 需要选音、制作和多设备试听 | 正式产品体验 |

推荐使用第三种：制作或选择一个独立的 Kin 消息提示音，同时保留系统默认声音作为资源加载失败时的降级方案。

### 10.3 声音方向

- 短促，建议约 180～350 毫秒。
- 温和、清晰，在环境声中能被察觉，但不尖锐刺耳。
- 可以使用轻微上行的双音或柔和木质/玻璃触碰感，呼应“靠近”和“连接”。
- 不使用类似警告、付款成功、系统报错或游戏奖励的声音。
- 消息、好友上线和语音来电必须使用不同节奏，避免误判。

### 10.4 音量与设置

- 提高应用内播放器音量，但不承诺绕过用户的系统媒体音量。
- 在系统音量约 30%、60% 和 100% 下分别试听。
- 在安静室内和有轻度环境噪声的场景测试。
- 保留设置页的“消息提示音”开关。
- 连续收到多条消息时沿用节流机制，避免连续响铃。
- Android 通知渠道创建后声音配置可能被系统保留；正式更换后台通知声音时可能需要新的通知渠道 ID 或引导用户重新设置。

## 十一、聊天输入区与语音模式

### 11.1 键盘遮挡输入栏

#### 现象

点击聊天输入框后，系统 26 键输入法覆盖底部输入栏，用户看不到正在输入的内容。

#### 当前代码结论

聊天页虽然使用了 `KeyboardAvoidingView`，但 Android 的 `behavior` 为空，因此组件不会执行明确的高度避让。Expo SDK 57 的 Android `softwareKeyboardLayoutMode` 默认是 `resize`，但官方文档同时说明透明状态栏场景仍可能需要 `KeyboardAvoidingView` 主动管理键盘布局；当前缺失的 Android `behavior` 是本次缺陷的直接原因。

#### 可选方案

1. 使用 Android `adjustResize` 或 Expo 对应键盘布局配置，并完善现有 `KeyboardAvoidingView`。
   优点是改动较小；缺点是部分定制系统仍可能存在差异。
2. 引入专用键盘控制库统一处理键盘高度和过渡。
   优点是控制更稳定；缺点是增加原生依赖，需要重新构建开发版 APK。

推荐先采用方案 1，并在当前两台手机和至少一种不同品牌设备上验证；只有兼容性仍不稳定时再采用方案 2。

验收要求：

- 键盘出现时，整行输入区始终位于键盘上方。
- 多行输入框增高时不能被键盘遮挡。
- 消息列表可见区域相应缩小，但当前阅读位置不能无理由跳动。
- 键盘关闭后布局平滑恢复。

#### 实施结果（2026-07-31）

- 聊天页在 iOS 继续采用 `padding` 键盘避让，在 Android 明确采用 `height`。
- 删除始终为零、没有表达有效差异的 `keyboardVerticalOffset` 配置。
- 键盘出现时，聊天页可用高度缩小，底部输入栏随之停留在系统键盘上方。
- 未增加新的原生依赖，也未修改全局 Android 键盘模式，降低对登录、注册和其他表单页面的影响。
- 已增加自动化回归检查；不同品牌输入法、多行输入框及打开/关闭动画仍需 Expo APK 真机验收。

### 11.2 文字与语音双模式

采用类似微信的明确模式切换。

文字模式：

```text
[语音图标] [聊天输入框                ] [表情] [发送]
```

语音模式：

```text
[键盘图标] [按住说话                  ] [表情] [发送]
```

交互规则：

- 点击语音图标进入语音模式，输入框替换为横向“按住说话”按钮。
- 左侧语音图标变成键盘图标。
- 点击键盘图标恢复文字模式并重新聚焦输入框。
- 用户已输入但尚未发送的文字必须保留，切换模式不能清空草稿。
- 语音模式下发送按钮保持原位置但进入不可用状态；选择表情后自动回到文字模式并插入表情。
- 长按“按住说话”开始录音，松开发送，上滑后松开取消。
- 录音状态应在长条按钮和上方提示区域同时反馈时长与取消状态。

### 11.3 一台设备录音失败

目前一台手机可以正常录音和上滑取消，另一台手机显示“录音失败，请重试”。现有代码会把录音权限、音频模式设置、录音器准备、文件生成和文件读取中的多种错误统一压缩成同一句提示，因此仅凭当前信息不能确定唯一原因。

专项诊断时需要记录：

- 手机品牌、型号和 Android 版本；
- 麦克风权限的真实状态；
- 音频模式设置是否成功；
- `prepareToRecordAsync`、开始录音、停止录音和读取临时文件分别在哪一步失败；
- 是否受到正在进行的语音通话、其他录音应用或系统音频焦点影响；
- 失败后的录音器是否能在下一次长按前正确重置。

用户提示需要按真实原因区分：

- `需要麦克风权限`
- `麦克风正被其他应用使用`
- `当前设备无法启动录音`
- `语音文件保存失败`

不能继续把所有情况都显示为“录音失败，请重试”。

### 11.4 点击语音键却显示“消息与在线状态已同步”

该提示属于全局 WebSocket 恢复状态，不属于语音功能。普通的语音模式切换和录音操作不应该触发它。

当前应用会在 App 从非 Active 状态回到前台时执行连接恢复。麦克风权限弹窗或某些设备的系统音频界面可能造成短暂 AppState 变化，进而被误判为需要恢复连接；这个触发链仍需通过真机日志确认。

修正规则：

- 只有应用确实经历离线、连接恢复或消息补同步时才展示同步提示。
- 短暂权限弹窗或音频模式切换不得展示“已同步”。
- 如果连接从未中断，不显示成功提示。
- 可以为恢复流程增加最短持续时间，过滤瞬时状态抖动。

## 十三、播放历史语音时保持滚动位置

### 13.1 真机现象

用户上滑查看较早的消息后，点击其中一条语音消息，页面会自动滚动到最新消息，导致当前阅读上下文丢失。

### 13.2 代码确认原因

当前聊天列表在任何内容尺寸变化时都会无条件执行 `scrollToEnd()`。语音气泡开始加载、播放状态改变或其他消息布局变化时，都可能触发内容尺寸回调，从而把列表强制拉到底部。

### 13.3 修复规则

- 播放、暂停或加载语音不得改变聊天列表位置。
- 只有以下情况允许自动滚到底部：
  - 首次进入会话并完成首屏历史加载；
  - 用户发送新消息且发送前已经位于底部附近；
  - 用户正在底部附近并收到新消息。
- 用户离开底部查看历史时，收到新消息只显示“有新消息”浮动提示，不自动抢走位置。
- 点击提示后才滚动到最新消息。
- 需要记录用户是否处于底部附近，不能继续依赖所有内容尺寸变化。

### 13.4 验收标准

- 在距离底部至少 10 条消息的位置播放多条语音，列表位置保持稳定。
- 播放、暂停和播放结束均不跳动。
- 收到新消息时历史阅读位置不变。
- 回到底部后，新消息继续保持自然跟随。

### 13.5 实施结果（2026-07-31）

- 已移除聊天列表在所有内容尺寸变化时无条件执行的 `scrollToEnd()`。
- 新增独立滚动策略，根据首次加载、明确滚动操作以及用户是否位于底部附近决定是否跟随。
- 用户查看历史消息时，语音加载、播放、暂停或结束造成的布局变化不再触发自动滚底。
- 用户离开底部后收到新消息时保留当前位置，并显示“有新消息”按钮；点击后才滚动到最新消息。
- 首次进入会话以及用户位于底部附近时，消息仍保持自然跟随。
- 已增加自动化回归检查；最终手感和语音播放场景仍需通过 Expo APK 真机验收。

## 十四、多账号本地聊天记录隔离

### 14.1 真机现象

同一台手机先登录账户 B 与账户 A 聊天，退出后再登录账户 C；账户 C 在与账户 A 的会话中看到了原本属于 B 与 A 的本地聊天记录。

### 14.2 代码确认原因

本地 `messages` 表只有消息 ID、聊天对象 `chat_id` 和发送者 `sender_id`，没有当前登录账号的 `owner_id`。读取历史消息时也只按对方用户 ID 查询。

因此同一设备上的 B 和 C 只要打开同一个聊天对象 A，就会查询到相同的本地会话记录。这不是服务端把 B 的消息发送给了 C，而是本地 SQLite 数据没有按账号隔离。

### 14.3 方案比较

| 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| 每个账号独立数据库文件 | 数据库名包含当前账号 ID | 隔离直观，删除账号数据方便 | 多数据库管理、迁移和导入导出更复杂 |
| 单数据库增加 `owner_id` | 所有消息查询和唯一约束都包含当前账号 | 延续现有架构，统计和迁移较集中 | 必须完整修改所有读写查询，漏改会继续串号 |

推荐使用“单数据库增加 `owner_id`”方案，因为联系人缓存已经采用同样的账号归属模型，可以形成一致的数据访问规则。

### 14.4 数据模型要求

- `messages` 表新增不可为空的 `owner_id`。
- 会话标识由 `owner_id + chat_id` 共同确定。
- 所有保存、读取、统计、删除、已读、重试、导入和导出操作都必须带当前账号 ID。
- 消息 ID 的唯一性需要结合服务端 ID 规则评估；必要时使用 `owner_id + id` 复合唯一键。
- 全局收件箱保存消息时必须记录当前接收账号。
- 退出账号不要求删除本地记录，但切换账号后只能读取新账号自己的数据。

### 14.5 迁移策略

现有旧消息没有可靠的 `owner_id`，不能猜测其归属。

可选方案：

1. 测试阶段直接清空旧的本地消息数据库。
   简单可靠，但会删除测试聊天记录。
2. 根据发送者和已知好友关系尝试迁移。
   能保留部分数据，但无法保证准确，可能延续隐私问题。

当前仍处于测试阶段，推荐方案 1：版本升级时明确清理旧测试消息，再以正确结构重新验证。实施删除前需要再次确认，因为它会清除设备上的现有测试聊天记录。

当前已确认采用测试阶段的简单可靠方案：

- 数据库升级时清理旧的本地测试聊天记录、会话摘要和相关未读状态。
- 新结构为消息增加当前登录账号归属，确保记录与账户绑定。
- 清理后使用测试账号 A、B、C 重新执行多账号隔离验收。
- 后续正式版本不得再依赖清库解决迁移问题，必须提供可审计的数据迁移策略。

### 14.6 严重程度与验收

该问题属于账号数据隔离和隐私缺陷，优先级高于视觉优化。

验收场景：

1. 手机 B 登录账户 B，与账户 A 发送多条文字和语音。
2. 退出账户 B，登录账户 C。
3. 账户 C 与账户 A 建立好友关系并进入聊天。
4. 账户 C 不得看到任何 B 与 A 的消息、摘要、未读数或导出记录。
5. 再切回账户 B，B 自己的本地记录仍然可见。

### 14.7 当前实现结果

`remodification-demo01` 分支已完成第一阶段代码修复：

- `messages` 表新增不可为空的 `owner_id`。
- 消息主键调整为 `owner_id + id`，相同消息 ID 不会跨账号互相覆盖。
- 历史读取、会话摘要、未读统计、已读状态、删除、发送状态、Outbox、导入和导出全部增加账号范围。
- 检测到旧消息表时自动清空旧测试消息并重建新结构。
- 导出的备份文件记录所属账号；其他账号不能导入该备份。
- 增加自动化回归检查，模拟 B 和 C 在同一设备上与共同好友聊天，验证双方只能读取自己的本地记录。

当前自动化检查和 TypeScript 类型检查已经通过，仍需在新 APK 中完成第 14.6 节的真实账号切换验收。

## 十五、配对名片缺少背景图片

### 15.1 真机现象

使用配对码完成配对时，双方都能看到对方名片，但已经设置背景照片的账户仍然只显示头像和文字，没有显示背景名片。

### 15.2 代码确认原因

配对服务返回的用户摘要只包含 ID、用户名、昵称和头像；移动端 `PairingPeer` 类型同样没有 `profile_banner`。因此背景图片从未进入配对会话数据，弹窗自然无法显示。

### 15.3 修复要求

- 后端配对用户摘要增加 `profile_banner`。
- 移动端 `PairingPeer` 类型增加对应字段。
- 创建、加入、轮询和 WebSocket 配对更新返回一致的数据结构。
- 弹窗按照第五章确定的规则显示：头像附近独立横向图片区、保持原比例、不裁剪、不拉伸、不铺满弹窗。
- 使用统一的媒体 URL 解析逻辑。
- 加载失败时显示稳定的默认名片背景，不能让布局塌陷。
- 修改背景后，新的配对会话必须读取最新图片。

### 15.4 验收标准

- 有背景图的双方都能在配对确认窗口看到对方背景。
- 没有背景图或图片加载失败时退回原有头像布局，不保留空白图片区。
- 配对码和 NFC 两种进入方式显示完全一致。
- 图片加载中、加载失败和弱网状态均不影响确认按钮使用。

### 15.5 实施结果（2026-07-31）

`remodification-demo01` 分支已完成配对名片背景的数据与界面闭环：

- 后端配对用户摘要增加 `profile_banner`，创建、加入、轮询和 WebSocket 更新共用同一份完整快照。
- 移动端 `PairingPeer` 类型增加背景名片字段，并复用统一媒体 URL 解析逻辑。
- 配对确认弹窗在头像附近增加独立横向图片区，使用 `contain` 保持原比例完整显示，不裁剪、不拉伸、不添加遮罩。
- 头像轻微压在背景名片下缘；没有背景图或图片加载失败时自动退回原有头像布局，确认流程与按钮不受影响。
- 增加后端服务回归测试和移动端源代码检查，防止后续再次遗漏字段或误改为裁剪填充。

当前自动化检查已通过，仍需在新 APK 中使用两个设置了不同背景名片的测试账号，分别验证配对码和 NFC 流程。

## 十六、可拖动半弹窗与抓手规范

### 16.1 当前问题

部分弹窗顶部显示抓手条，视觉上暗示用户可以按住拖动、调整高度或关闭窗口，但当前抓手只是静态装饰，点击或拖动没有反应，因此产生明显的“假交互”感。

现有添加好友半弹窗中的抓手就是普通 `View`，没有手势处理。这一问题可以从代码确认。

### 16.2 可选方案

| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| 保留静态弹窗并移除抓手 | 实现简单，不再产生错误暗示 | 不能手动调节窗口 | 内容固定、无需拖动的确认弹窗 |
| 实现统一可拖动 Bottom Sheet | 符合用户预期，可拖动展开和关闭 | 需要手势、动画、键盘和无障碍处理 | 内容较多或存在不同高度状态的弹窗 |

推荐规则不是“所有弹窗都必须能拖”，而是：显示抓手就必须支持拖动；不需要拖动的弹窗就不要显示抓手。

碰一碰等待和名片确认窗口内容会随状态、名片图片和错误信息变化，推荐使用统一的可拖动 Bottom Sheet。

### 16.3 交互规范

- 抓手本身及其周围区域共同构成足够大的拖动热区。
- 用户可以拖动抓手，也可以从弹窗顶部非交互空白区域开始拖动。
- 支持至少“默认高度”和“展开高度”两个停靠点。
- 向下拖动超过阈值可以关闭，但正在进行双方确认等关键流程时需要二次确认或回弹，不能误触即取消。
- 内容不足时不允许无意义地拉伸出大片空白。
- 弹窗内部滚动与整体拖动需要正确协调。
- 键盘打开时，弹窗不能被键盘覆盖或错误关闭。
- 减少动态效果模式下缩短或取消弹性动画，但保留位置变化。
- 为读屏用户提供等价的“展开”“收起”“关闭”操作，不能只依赖拖动手势。

### 16.4 组件化要求

后续应建立统一的 Kin Bottom Sheet 组件，集中处理：

- 遮罩淡入淡出；
- 弹出和回弹动画；
- 拖动手势与停靠点；
- 安全区和键盘避让；
- 关闭策略；
- 焦点管理与无障碍；
- 减少动态效果；
- Android 返回键。

不应在每个页面分别复制一套抓手和弹窗逻辑。

### 16.5 实施结果（2026-07-31）

`remodification-demo01` 分支已建立首个统一 `KinBottomSheet` 组件，并完成碰一碰弹窗迁移：

- 使用 React Native 内置 `PanResponder` 与 `Animated`，未增加第三方原生依赖。
- 提供默认高度和展开高度两个停靠点，可通过顶部 52dp 拖动热区上下拖动。
- 普通结束状态支持向下拖动关闭；等待加入和双方确认等活动配对状态误拖时会回弹，不会直接取消会话。
- 组件集中处理遮罩、进入/退出动画、安全区、键盘避让和 Android 返回键。
- 支持系统“减少动态效果”，关闭弹性与长动画，仅保留必要的位置变化。
- 为读屏提供展开、收起和关闭操作，并在弹窗打开时把无障碍焦点移入弹窗。
- 碰一碰内容区改为可滚动区域，底部确认按钮保持独立，较小屏幕和大字体下不再依赖固定内容高度。
- 增加源代码回归检查，防止页面重新复制原始 `Modal` 或恢复静态假抓手。

当前自动化检查已通过，仍需在 Android APK 中验收拖动手感、大字体、TalkBack、系统返回键及活动配对防误关闭行为。其他弹窗尚未迁移，后续只在确实需要拖动的场景复用该组件。

## 十七、全局 Graphite Flow 高级黑主题与主导航

| 层级 | 用途 | 要求 |
|---|---|---|
| 页面基底 | 全屏背景 | 接近黑色的哑光石墨色，避免死黑造成层级消失 |

| Kin 绿 | 在线、选中、主操作、成功连接 | 低饱和使用，不能大面积铺满页面 |
| 警告与错误 | 失败、危险操作 | 使用独立语义色，不能用 Kin 绿表达错误 |

- 正文、输入内容和关键按钮必须满足可读性与无障碍对比度。
- 深色主题下显式设置文字、占位符、光标和选中颜色，不能依赖系统默认值。
- 阴影只用于悬浮导航、头像、弹窗等确有层级变化的元素。
- 不使用高亮霓虹绿、大面积纯绿色背景或持续发光效果。
- 图片、头像和用户背景可以保留自身颜色，但周围组件仍遵守统一深色层级。

通用要求：

### 17.5 “会话”页面结构

“会话”继续承担在线感知和最近聊天两个核心职责，保留：

1. `Online`：当前在线好友，使用圆形头像和在线状态点快速浏览。
2. `最近会话`：展示最近消息摘要、时间和未读数。
3. `Offline`：展示当前离线好友及其最近会话状态。

要求：

- Online、最近会话和 Offline 必须具有清晰但克制的分组层级。
- 好友状态变化遵循第六章确定的三阶段上线动画。
- 点击在线头像或会话行均可进入聊天详情。
- 碰一碰入口可以保留在页面右上角，但不能取代通讯录页中的添加好友入口。

已确认采用紧凑状态区方案：

- Online 使用横向圆形头像作为快速入口。
- Offline 使用紧凑或可折叠区域，避免离线好友较多时占据整个页面。
- 最近会话继续作为页面主要列表。
- 同一好友可以同时出现在 Online/Offline 状态区和最近会话中，因为两个区域分别表达“当前状态”和“聊天历史”。
- 多处出现的同一好友必须共享一致的头像、昵称、在线状态和未读数据源。

### 17.6 “通讯录”页面结构

“通讯录”用于展示全部好友和进入添加好友流程：

- 顶部提供好友搜索。
- 全部好友按昵称拼音或字母分组排列。
- 支持快速定位字母分组；好友数量较少时可以不显示固定侧边索引，但数据顺序仍按拼音处理。
- 好友行展示头像、昵称和必要的 Online/Offline 状态。
- 页面提供明确的碰一碰/添加好友入口。
- 点击好友进入聊天或好友详情，最终入口行为在实现前结合现有路由确认。

点击行为已确认：

- 点击好友行主体直接进入与该好友的聊天页面。
- 点击好友头像进入对方的好友资料页面。
- 头像点击区域需要独立且足够大，不能因为事件冒泡同时打开聊天页面。
- 好友资料页提供明确的“发消息”入口，可返回该好友聊天。

拼音排序需要明确处理英文昵称、中文昵称、数字、符号和昵称缺失等边界情况，不能简单依赖设备语言产生不一致顺序。

### 17.7 “我的”页面结构

“我的”对应第十二章确定的独立个人主页/Profile Card：

- 顶部显示用户独立上传的背景图。
- 使用圆形头像，头像贴合背景与主体交界位置。
- 显示昵称、用户 ID 和有意义的在线状态。
- 主体采用方案 A 的两列功能卡片。
- 包含我的名片、个人资料、通知与状态、账户与安全、聊天数据、帮助与法律。
- 设置作为个人页内的明确入口，不再与 Online/Offline 并列成为主页面。

### 17.8 聊天、设置与弹窗落地规则

聊天页面：

- 聊天背景使用页面基底色；对方消息使用深色表面，自己的消息使用克制的深绿色表面。
- 自己和对方的气泡必须依靠位置、颜色和圆角同时区分，不能只依赖绿色。
- 输入栏、语音模式、更多操作面板和键盘上方区域使用统一深色组件。

设置页面：

- 使用深色分组卡片和清晰的层级标题。
- 开关开启状态使用 Kin 绿，关闭状态仍需清晰可辨。
- 危险操作与退出登录不得使用 Kin 绿，需要使用独立警示语义。

弹窗与 Bottom Sheet：

- 使用比页面基底略亮的深色表面，并配合遮罩建立焦点。
- 遮罩只压低弹窗外内容，不覆盖或改变弹窗中的名片背景图片。
- 按钮、说明文字和取消操作必须具备足够对比度。
- 延续第十六章规则：显示抓手就必须支持拖动；静态弹窗不显示假抓手。

碰一碰入口规则：

- 会话页右上角保留碰一碰快捷入口。
- 通讯录页保留主要的添加好友/碰一碰入口。
- 两个入口进入同一页面并共享同一配对会话状态。
- 如果一处已经开启碰一碰，从另一处进入时必须显示当前状态，不能重复创建配对会话。

### 17.9 实施边界与验收

建议先建立可复用的全局主题 Token 和基础组件，再逐页迁移。禁止在每个页面分别硬编码一套近似黑色。

验收至少包括：

- 登录前、登录后、聊天和弹窗之间视觉连续。
- 当前测试 Android 真机上没有白底闪烁、白色系统默认输入框或文字不可见问题。
- 会话、通讯录和我的三个入口均可到达，返回关系明确。
- 深色表面之间仍能辨认层级，不因全部使用黑色而混成一片。
- Kin 绿只承担强调和状态职责，不造成视觉疲劳。
- 系统开启大字体、减少动态效果或屏幕亮度较低时仍可使用。

## 十九、潜在影响

### 正面效果

- 降低用户理解 NFC 技术角色的负担。
- 让碰一碰流程更接近自然见面时的行为。
- 强化 Kin 的个人身份表达和视觉辨识度。
- 让消息发送、上线和配对成功具有更完整的情绪节奏。
- 登录注册与主应用形成统一产品形象。
- 避免同一设备切换账号时暴露其他账号的本地聊天记录。
- 让键盘、语音播放和半弹窗交互符合用户已有的移动端习惯。
- 个人主页从设置表单升级为真正的身份展示入口。
- 全部页面形成连续的 Graphite Flow 品牌体验，不再出现深浅主题割裂。
- “会话 / 通讯录 / 我的”让最近聊天、全部好友和个人功能各自拥有清晰归属。

### 风险与注意事项

- 单一碰一碰按钮需要底层可靠完成角色分配，不能只隐藏按钮而保留冲突的技术流程。
- NFC 能力受设备品牌、系统版本和前后台状态影响，必须经过真机验证。
- 配对接口加入背景图会增加网络请求和图片加载失败状态。
- 用户上传图片不能破坏身份核验、文字可读性和弹窗操作稳定性。
- 新增动画会增加低端设备性能压力，需要使用高性能属性并支持降级。
- 测试账号方案不能被误带入正式版本。
- 本地消息增加账号归属字段需要数据库迁移；测试阶段推荐清理旧消息，但执行前必须确认。
- 新增头像上传会影响后端媒体接口、缓存和实时资料同步。
- 自定义消息提示音需要同时处理应用内声音与系统通知渠道。
- 可拖动 Bottom Sheet 需要谨慎处理滚动、键盘、误关闭和无障碍。
- 全局深色迁移涉及登录前后所有页面和基础组件，若缺少统一 Token，容易产生大量难以维护的局部色值。
- 深色表面的层级差异较小，需要在不同亮度、不同屏幕和户外环境中验证可读性。
- 新增通讯录和个人主入口会改变现有页面导航结构，正式实施前需要梳理路由、返回行为和各标签状态保留策略。
